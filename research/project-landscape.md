## 项目技术分析

### 1. LiteLLM — TokenRouter
- 用途：统一不同模型提供商的调用协议；研究 chat、messages、responses 类型的参数映射、流式响应、上游重试和故障转移。
- 可复用形态：优先研究协议适配设计与兼容性测试用例；不直接套入整个网关取代现有计费与鉴权。
- 关键接口：OpenAI 风格 API、Anthropic 风格 API；具体支持范围随版本变化。
- 验证：两种上游模型、正常/流式/工具调用/错误请求至少四组。
- 风险：双层路由使错误归因复杂；套餐或企业功能不能推定为全部开源。

### 2. Langfuse — TokenRouter + 智脑
- 用途：Trace、Span、延迟、成本、Prompt 与 RAG 质量观察。
- 可复用形态：先旁路发送经脱敏的测试调用信息，不替换原有账单系统。
- 验证：超时、429、上游 5xx、多步骤 Agent 能否形成一条可理解的链。
- 风险：Trace 数据可能包含 Prompt、回答、个人信息；储存服务和企业级能力需审核。

### 3. RAGFlow — 晨羽智脑
- 用途：复杂 PDF、扫描件、表格解析与基于检索的问答；评估版式和引用准确性。
- 可复用形态：独立解析服务 PoC，与现有智脑文档管线做 A/B。
- 验证：至少十份获授权的脱敏文档，比较表格保留、召回、引用及资源消耗。
- 风险：OCR、索引和模型依赖；文档格式支持应按版本实测。

### 4. New API — TokenRouter 竞品
- 用途：渠道、模型、Key、额度、用量、平台运营功能研究。
- 可复用形态：功能差异矩阵和架构对照，不复制 UI 或代码。
- 验证：按模型适配、成本控制、API 密钥和审计能力制作对照表。
- 风险：AGPLv3 网络服务义务、NOTICE 署名等特殊许可条件。

### 5. Dify — 晨羽智脑
- 用途：可视化 Agent、RAG 和工作流编排。
- 可复用形态：产品交互/低代码操作路径研究，必要时隔离部署演示。
- 验证：三节点工具调用、知识库问答、审批中断、失败恢复等操作路径。
- 风险：Dify Open Source License 存在额外条件，尤其多租户、前端品牌。

### 6. n8n — 两款产品
- 用途：定时/事件触发、API 调用和系统集成。
- 可复用形态：通过 HTTP API 做联调，不把其代码嵌入网关。
- 验证：事件触发 → 调用智脑测试 API → 产出结果 → 错误分支。
- 风险：Sustainable Use License 并非通用宽松开源许可，商业再分发需检查。

### 7. vLLM — 晨羽 AI 服务器
- 用途：高吞吐推理服务、OpenAI 兼容接口以及批处理调度。
- 可复用形态：作为独立模型服务供 TokenRouter 调用。
- 验证：RTX 4090D/5090 等实际环境中的 CUDA/驱动、权重格式、TTFT、token/s、并发、显存。
- 风险：硬件支持和量化支持取决于版本；不要从宣传数字推定实际吞吐。

### 8. OpenHands — Agent
- 用途：自主处理编程任务的工具调用、沙箱执行与 GitHub 开发流程。
- 可复用形态：独立部署、按权限接入模型网关。
- 验证：只对测试仓库执行文件修改、单测和 PR 草稿；限制网络与命令权限。
- 风险：自动执行代码有供应链、权限和费用风险。

### 9. Open WebUI — 产品体验
- 用途：聊天、模型选择、文件交互、用户/配置操作研究。
- 可复用形态：仅功能与 UX 对标。
- 验证：评估多模型切换、首屏接入和新手操作步骤。
- 风险：当前许可证含品牌保留要求，白标/转售需核查。

### 10. One API — 历史架构参考
- 用途：模型渠道抽象、令牌、配额与映射机制。
- 可复用形态：和 New API 横向比较，提取需求，不直接引入旧版核心代码。
- 验证：可扩展性、协议兼容和安全维护状态与当前 TokenRouter 对比。
- 风险：具体分支的许可证、依赖和维护状态均需版本级审计。

## 结论

**立即测试：LiteLLM、Langfuse、RAGFlow。**
**下一阶段：vLLM、Dify、n8n、OpenHands。**
**竞品与产品对标：New API、Open WebUI、One API。**

所有项目都只能在隔离 PoC 环境中验证。禁止在未完成许可审查、软件成分表（SBOM）和安全验证前直接用于商业交付。
